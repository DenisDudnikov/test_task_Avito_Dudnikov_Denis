Решение вкратце:
1) Есть несколько строгих фильтров, по которым выбираются потенциальные объявления. Эти фильтры получены путём анализа - пользователи почти никогда не выбирали объявления, которые им не соответствуют.
2) Также применяются мягкие фильтры - они добавляют объявлению скор, но не отсеивают кандидата, если он не соответствует.
3) Небольшой процент объявлений из бенчмарка присутствуют в трейн датасете. Если попадается похожий запрос - это объявление добавляется в топ-50 т.к при тех же условиях на него уже когда-то жали.
4) BM25 - получает скор по соответствию текста запроса и заголовка/описания объявления.
5) Очень важный параметр, наравне с BM25 - расстояние от пользователя до места размещения объявления. В зависимости от редкости запроса и расстояния вычисляется скор. Пользователь вряд ли поедет в другой город за стрижкой или будет вызывать сантехника за 500 км, но что-то редкое, вроде изготовки гос номеров, может потребовать поездки.

Объявления сортируются по этому скору и берётся топ-50. Конкретные коэффициенты вычислялись скриптом tune_hyperparams.py на данных из train.

# Генерация кандидатов для поиска объявлений (Recall@50)

Для каждого поискового запроса решение выбирает до 50 `item_id` из корпуса объявлений, которые дальше уходят на ранжирование. Метрика — **Recall@50**: доля подходящих объявлений, попавших в топ-50. Порядок внутри 50 и «лишние» кандидаты не штрафуются.

Решение — гибрид **классического IR (BM25 со стеммингом)** и **строгих правил-фильтров, проверенных на реальных данных**. Нейросети и эмбеддинги в финальной версии не используются, обучения нет, внешних API нет, всё считается локально на CPU.

## Запуск

```bash
pip install -r requirements.txt

# 1. Финальный ответ для отправки
python candidates_pipeline.py \
    --train train.parquet --queries benchmark_queries.parquet \
    --items benchmark_items.parquet --labels nazvaniya_filtrov.csv \
    --output answer.csv

# 2. Прокси-валидация Recall@50 (распределение holdout приближено к бенчмарку)
python validate_holdout.py --train train.parquet --items benchmark_items.parquet \
    --labels nazvaniya_filtrov.csv --n-eval 1500 --match-benchmark

# 3. Подбор гиперпараметров (по желанию)
python tune_hyperparams.py --train train.parquet --items benchmark_items.parquet \
    --labels nazvaniya_filtrov.csv --n-tune 1000 --n-confirm 1000
```

Формат `answer.csv`: колонки `query_id`, `answer` — до 50 `item_id` через пробел. Скрипт проверяет, что `query_id` не повторяются и число строк равно числу запросов.

## 1. Какие данные и признаки использованы и почему

### Данные

| Файл | Как используется |
|---|---|
| `benchmark_items.parquet` (189 212 объявлений) | Корпус, по которому идёт поиск. Из него строятся BM25-индекс, маски фильтров и координаты локаций. |
| `benchmark_queries.parquet` (2452 запроса) | Запросы, для которых генерируются кандидаты. Разметки нет. |
| `train.parquet` (497 673 пары запрос → выбранное объявление) | Три роли: (а) **lookup-слой** — точный текст запроса → уже выбранные `item_id`; (б) **достройка координат** локаций, которых нет в корпусе; (в) **holdout для проверки качества и подбора параметров**. Также на нём измерена надёжность каждого фильтра. |
| `nazvaniya_filtrov.csv` | Справочник из 63 названий фильтров, собранный вручную по частотному анализу `infm_params_text`. |

### Признаки и почему они выбраны

Каждый признак выбирал по данным train: насколько он надёжен на реальных парах «запрос → выбранное объявление».

| Признак | Как используется | Обоснование |
|---|---|---|
| `search_query`, `item_title_raw`, `item_description_raw`, `item_infm_params_text` | Текст для BM25. Заголовок повторяется 3 раза (`TITLE_REPEAT`), к нему добавляются параметры и описание. К запросу добавляется и текст его фильтров. | Заголовок — самый сильный лексический сигнал. |
| `search_category` / `item_category_id` | **Жёсткий фильтр** `==`. Исключение: `search_category == 0` → фильтра нет. | Совпадение на train 99.99%. Значение 0 никогда не встречается среди `item_category_id`, а тематика таких запросов разнородна, поэтому 0 трактуем как «категория не выбрана». |
| Фильтр «Рейтинг пользователя N звезды и выше» (из `search_infm_params_text`) → `item_rating` | **Жёсткий фильтр** `item_rating >= N`. Объявление без рейтинга (NaN) фильтр проходит. | На 856 train-строках порог выполняется в 99.76% случаев. NaN пропускаем, потому что отсев ради строгости дороже для recall. |
| Метка «Вид услуги» (запрос ↔ объявление) | **Жёсткий фильтр**: пересечение значений (OR внутри метки). Если у объявления метки нет, значение ищется в его сыром тексте. | 98.4% прохождения на 316 860 реальных пар. |
| Остальные метки `infm_params_text` («Тип услуги», «Тип услуги автосервиса», «Кто оказывает услуги», …) | **Только мягкий сигнал**: доля совпавших меток добавляется к скору с весом `SOFT_MATCH_WEIGHT`. | Прохождение на реальных парах от 0% до 87%, отсев по ним резал бы recall. |
| «Онлайн-запись» | Проверка **наличия** метки у объявления, не сравнение значений. | Это артефакт виджета бронирования, значения не совпадают ~никогда. |
| «Слова в описании» | Сравнение с `item_description_raw`, а не с параметрами. | По смыслу это keyword-фильтр по описанию. |
| `search_location_id`, `item_location_id`, `item_latitude/longitude` | **Не фильтр.** Плавный бонус `LOCATION_BONUS·exp(−dist/decay)` и адаптивное сужение пула для частых запросов (подробнее в разделе 2). | Локация совпадает точно только в 83.1% случаев. У несовпадающих 17% медиана расстояния 34 км, но 90-й перцентиль 502 км, 99-й 3227 км, максимум ~15 000 км. Надёжного радиуса нет. |
| `search_is_delivery_search` | Для запросов с доставкой локация не учитывается вовсе (ни бонус, ни сужение). | Для доставки расстояние не важно. |
| `item_rating_reviews_count` | Ранжирование в последнем фолбэке («популярные объявления категории»). | Простой запасной критерий, когда текстовых кандидатов не хватает. |

Не использованы: `item_price`, `item_microcat_id`, `item_is_phone_hidden`, `item_is_message_forbidden`.

## 2. Какие модели и алгоритмы применены

Обучаемых моделей нет. Пайплайн детерминирован (стабильная сортировка, тай-брейк по `item_id`). Пайплайн полностью лексический (BM25 + правила).

### Шаги для каждого запроса (`assemble_candidates_for_query`)

1. **BM25.** Индекс строится один раз: `CountVectorizer` с собственным токенизатором (нижний регистр, стоп-слова, стемминг `nltk SnowballStemmer('russian')` с кэшем), затем веса BM25 (`k1=0.9`, `b=0.5`) в CSC-матрице. Скор запроса — сумма `idf × вес` по колонкам его термов, без пересчёта матрицы.
2. **Бонус за близость.** К скору добавляется `LOCATION_BONUS · exp(−dist / decay)`, где `dist` — расстояние от локации запроса до объявления. Для локаций, чьи координаты достроены, масштаб `decay` учитывает их разброс. Если координат локации нет вообще, бонус выдаётся по точному совпадению `location_id`.
3. **Жёсткий фильтр** по категории, рейтингу и «Виду услуги».
4. **Адаптивное сужение по локации.** Если после текста и фильтра кандидатов больше 300 (типовой запрос вроде «маникюр»), сначала берём ту же локацию, при нехватке (< `LOCATION_NARROW_MIN_POOL`) расширяем радиус: 20 → 60 → 150 → 300 → 800 км. Это **дополнительный приоритетный тир**, старые тиры остаются страховкой.
5. **Lookup-слой.** Если точный текст запроса встречался в train и его `item_id` есть в корпусе, они идут первыми. Такое совпадение есть у 14.68% текстов запросов бенчмарка, поэтому слой вспомогательный, а не основной.
6. **Тиры с постепенным ослаблением фильтра.** Порядок: все жёсткие фильтры → без «Вида услуги» → только категория → без фильтров. Внутри тира берётся пул из `POOL_SIZE` лучших и ре-ранжируется по `BM25 + LOCATION_BONUS·близость + SOFT_MATCH_WEIGHT·мягкий_скор`.
7. **Добор** самыми популярными объявлениями категории, если кандидатов всё ещё меньше 50.

### Основные параметры (`candidates_pipeline.py`)

| Параметр | Значение |
|---|---|
| `TOP_K` / `POOL_SIZE` | 50 / 400 |
| `BM25_K1` / `BM25_B` | 0.9 / 0.5 |
| `TITLE_REPEAT` | 3 |
| `LOCATION_BONUS` / `PROXIMITY_DECAY_KM` | 0.338 / 29.88 |
| `SOFT_MATCH_WEIGHT` | 2.979 |
| `LOCATION_NARROW_TRIGGER` / `LOCATION_NARROW_MIN_POOL` | 300 / 20 |
| `LOCATION_RADIUS_STEPS_KM` | 20, 60, 150, 300, 800 |

Значения бонусов и весов подобраны `tune_hyperparams.py` на holdout (см. раздел 3).

## 3. Как проверяи качество перед отправкой

У бенчмарка нет разметки, поэтому качество измеряли **прокси-валидацией на train** (`validate_holdout.py`):

1. Поиск идёт по **настоящему корпусу** `benchmark_items` (189k объявлений).
2. В holdout берутся только строки train, у которых верный `item_id` **есть в корпусе** (~9.6% train). Иначе верный ответ недостижим, и проверка была бы нечестной.
3. Псевдо-запрос использует **все признаки строки** (текст, фильтры, категорию, локацию, delivery), как реальный.
4. **Без утечки:** lookup-слой строится без текстов holdout-запросов (`exclude_texts`), иначе он «подсматривал» бы верный ответ.
5. **Распределение приближено к бенчмарку** (`--match-benchmark`): группы по частоте текста запроса в train — не встречался 63%, 1–10 раз 29.6%, >10 раз 7.4% — и 9.1% запросов с `search_category = 0` (в holdout у случайных строк категория принудительно обнуляется).
6. Метрика печатается **в разбивке по частоте текста запроса** и по категории 0, чтобы видеть, где именно работают сужение по локации и lookup.
7. Есть A/B-флаги: `--disable-narrow`, `--no-extend-locations`, `--soft-match-weight`, `--location-bonus` и др. Каждое решение (сужение, достройка координат, вес мягкого скора) проверялось сравнением с выключенным вариантом.
8. **Защита от переобучения при подборе параметров** (`tune_hyperparams.py`): holdout делится на две непересекающиеся части. По TUNE идёт поиск (случайный, затем локальный), лучшие конфиги перепроверяются на CONFIRM. Новый конфиг принимается, только если прирост на CONFIRM больше 1.5 стандартных ошибок (при n = 1000 SE ≈ 1.1 п.п.), иначе остаются прежние значения.
9. Фильтры до включения в пайплайн проверялись на **реальных парах train**: полный AND-фильтр по всем 63 меткам пропускал только 82.41% верных пар, и именно поэтому жёстким оставлены лишь три самых надёжных условия.

**Ограничения такой проверки.** Holdout — это ~9.6% train, где верный ответ лежит в корпусе бенчмарка. Это приближение, а не точная копия бенчмарка, поэтому абсолютные значения Recall@50 на holdout и на лидерборде могут отличаться. Для сравнения конфигураций между собой оценка пригодна. Итоговое значение proxy-Recall@50 нужно записать здесь после финального прогона: `Recall@50 (proxy, n=…) = …`.

## 4. Какие типы ошибок обнаружил и что с ними сделал

| Проблема | Как обнаружил | Что сделал |
|---|---|---|
| `item_price`, `item_latitude`, `item_longitude` читаются из parquet как `object` (Decimal) | EDA типов | Явная конвертация `to_float`: `pd.to_numeric(..., errors="coerce").astype(float)`. |
| Наивный парсер `infm_params_text` («резать по каждой заглавной») ломал аббревиатуры («ИП», «СПА») | Ручной разбор выборки | Сначала запрет резать между двумя заглавными подряд, затем переход на парсер по **курированному списку из 63 меток** (`nazvaniya_filtrov.csv`); длинные метки идут раньше коротких. |
| Короткие метки ложно матчились внутри слов («Пол» в «Полины», «Цвет» в «Цветочная») | Разбор ложных срабатываний | В regexp добавлены границы слова: `(?<![а-яёА-ЯЁa-zA-Z])(…)(?![а-яё])`. |
| Метка с пустым значением молча выпадала из словаря (случай «Рейтинг … звезды и выше Вид услуги X»), из-за чего проверка рейтинга могла не срабатывать | Перепроверка фильтров на train | В `parse_infm_params` метка добавляется в результат всегда, даже без значения. Более ранняя оценка надёжности рейтинга (regex напрямую по тексту) на баг не опиралась. |
| Полный AND-фильтр по всем меткам пропускал лишь 82.41% верных пар; «Тип услуги автосервиса» — 9.0%, «Кто оказывает услуги» — 13.7% (у объявления часто нет метки), «Тип услуги» — 86.6% | Замер прохождения каждой метки на реальных парах train | Жёстких фильтров оставлено три (категория, рейтинг, «Вид услуги»), остальные метки перенесены в мягкий скор. |
| «Онлайн-запись» (~0% совпадений значений) и «Слова в описании» (~15%) сравнивались неправильно по природе | Та же таблица надёжности | Первая — проверка наличия метки, вторая — сравнение с `item_description_raw`. |
| Локация: 17% верных ответов не в той же локации, хвост расстояний до ~15 000 км, радиус 200 км покрывает лишь 84% таких случаев | Расчёт расстояний на train | Ни точного, ни радиусного фильтра. Только плавный бонус за близость и адаптивное сужение как **добавочный** тир со страховкой в виде старых тиров. |
| `search_category = 0`: в train почти нет (34 строки), в бенчмарке 9.05%; совпадение с категориями 114 в train — статистический шум | Сравнение распределений train ↔ benchmark, разбор тематики запросов | При 0 категория не фильтруется. Holdout дополнительно содержит 9.1% таких запросов. |
| Отсутствующий рейтинг объявления | Анализ порога рейтинга | NaN считается прошедшим фильтр, чтобы не терять recall. |
| ~17% запросов имеют `search_location_id`, которого нет среди объявлений корпуса, без координат не работали ни бонус, ни сужение (recall на таких запросах на holdout ~0.43 против 0.87–0.96 на остальных) | Разбивка holdout по известности локации | `extend_location_coords`: координата = медиана координат объявлений, выбранных в train из этой локации, разброс задаёт масштаб бонуса; слишком «размазанные» локации (> `EXTEND_MAX_SPREAD_KM`) остаются неизвестными. |
| Утечка при валидации: lookup «угадывал» верный ответ по тексту самого holdout-запроса | Логический разбор схемы проверки | Тексты holdout-запросов исключаются из lookup (`exclude_texts`). |
| Подгонка гиперпараметров под шум | Оценка стандартной ошибки | Разбиение TUNE/CONFIRM и порог принятия 1.5·SE. |
| Недетерминизм при равных скорах | Разные результаты между запусками | Стабильная сортировка (`kind="stable"`) и вторичный ключ `item_id`. |
| Holdout с равномерной выборкой не похож на бенчмарк (в бенчмарке 63% запросов редкие и 9% с категорией 0) | Сравнение частот текстов | Стратифицированная выборка `BENCH_STRATA` и `BENCH_CAT0` (флаг `--match-benchmark`). |
